# Scarlet

Scarlet is a desktop-only video editor for macOS and Windows. Open projects, demonstrate features, take screenshots, and verify interface changes in the native Scarlet application window. Do not open or publish a browser version, including a localhost demo or an in-app browser preview.

Starting a chat does not require opening Scarlet. Keep code work and automated tests headless until the task needs the native interface. For work on the installed release, reuse the regular Scarlet window.

Silence only the Scarlet instance under test. Leave system volume, output devices, and other apps’ audio unchanged. For screenshots, use a muted native background preview and capture only the requested window or panel. On Windows, use a separate, noninteractive desktop and a disposable WebView2 profile. Launch with `--mute-audio` and verify the flag on that instance’s running WebView2 process before testing or capturing. Leave the user’s desktop, window focus, mouse, and keyboard untouched throughout.

Share one native preview across chats. Before launching, check for a running dev or demo session in the checkout you need. Reuse it if it is idle and matches the requested mode. If another chat is using the preview, wait your turn. When a preview needs to be started, use `pnpm desktop:dev` for the real project library or `pnpm desktop:demo` for the isolated sample interview. Close a temporary preview you started and stop its dev command after verification, unless the user wants it left open for review.

The React code in `apps/web` is the embedded Tauri renderer. Vite is its development asset server, and `apps/server` is the headless engine. Neither is a user-facing way to launch Scarlet.

On this Mac, install regular releases at `/Applications/Scarlet.app` and use that path for Dock shortcuts and handoffs. When updating Scarlet, replace the app at that path. After verifying a local build, eject its installer image and clean up staging copies, launchable backups, and superseded installers created by the task. Give intentional review builds a distinct name and bundle identifier, and preserve them while in use.

The local main updater manages that installation while enabled. Let it install verified commits from GitHub `main` after regular Scarlet quits. Use the shared native preview to try uncommitted changes. Create a separate review app only when the user explicitly requests a standalone build or the task requires testing the packaged app itself.

Keep the interface mostly black, white, and gray. Use small color accents for branding, voice, and status. Use the project's own footage for thumbnails and avoid decorative background images.

The editor chose a few quiet touches, and they stay. Ambient light: the footage's own colours glow softly round the player and under the timeline, following the picture (`AmbientLight`); it is the one light from the footage, not a background image. An edit applied while the editor watches lands with a moment on the timeline: its marker pops in with one ring, after a cut's red closes up where the footage came out. While the mic records, a ring round it moves with the voice. Timeline pictures fade in as they load, the card rises into place as it opens, and the playhead glides to a new position on a seek and jumps instantly across footage the player skips. A project's card flips through a few frames of its footage while the pointer rests on it. With motion reduced, none of it moves.

Use the shared `PreferenceSelect` for dropdown fields throughout the renderer, including compact toolbar and review pickers.

The simple view is one conversation on the left (`.simple-thread`), then the player with its card and timeline. There is no list of edits beside the chat. Every request for an edit is in the conversation in the order asked, headed by the editor's words, and it opens at the latest. A request about one cut or edit sits under that cut's or edit's row while Scarlet works on it or when it stopped early, and leaves once it has changed that cut or edit: what it did is there. Nothing in it is hidden or moved when a cut or an edit opens. The chat holds what was said and done, not the dialogue. While a cut or an edit is open, nothing sits over the message box: its transcript icon and Undo edit are on its card. Scarlet's note on a cut or an edit is on its card, once, and never repeated in the chat. The message box talks to the cut or edit that's open, and carries a tag before the text that says which ("Cut at 2:05", "Edit at 0:11"). An applied edit's tag reads as its row in the list does: at the row's time, and as a cut when it took footage out. A call of the pass that's waiting is tagged with its number instead ("Cut 2"). A request sent that way is headed with the same words in the chat and tagged with them in the queue. With nothing open the box answers Scarlet's question when one is waiting, tagged "Answer"; otherwise it starts a new edit. A new request starts on the whole video, whether the editor types, speaks or uses a slash command. A press or scrub on the timeline or a skip with ← → offers Edit here beside the input. The request takes that time only when the editor presses Edit here. N also takes the current time, stops the video and puts the cursor in the box. Either action tags the input "At 18:28". That tag belongs to the box alone and stays at the chosen time while the message is written. The request's heading in the chat and its line in the queue omit it. An empty box drops the tag once the video plays or moves on. Looking around the timeline keeps a draft, an open cut or edit, and an answer aimed where they were. The × on the tag makes the message a new edit about the whole video instead. A message being written stays aimed where it was, and then a line above the box names where and offers to bring it along: Move here, or New edit instead when nothing is open or asked. Otherwise that line is for screen readers only. While a pass still runs, a flagged cut Scarlet hasn't checked is not a call: it gets no dot or count until Scarlet asks about it. A call's number is the order it reached the editor in: Scarlet's asks as it makes them, then the cuts it never checked, in timeline order after them. A call keeps its number as later ones arrive, and it is the same on the timeline, on its card and in the pass's list. While the pass waits on calls, an edit of its request that asks for a look is numbered after them, in timeline order, and goes by that number in the list, on the timeline, on its card and in the box's tag ("Cut 6", or "Edit 6" when it took no footage out), so "N need you" is one run of numbers. Every one of them keeps the number it was first shown under for as long as the pass waits, kept or not: a call or an edit that arrives later takes the next number, wherever it is in the video, and a number whose call or edit has gone isn't given again. A call sent back for revision can't be opened from the pass's list, but ↑ and ↓ step through it like any call: its card says Revising…, Queued or Needs your answer where the decisions were, and when its revision lands the card stays open on the new version. The chat can't be dragged under 320px. The editor chose this design. Get their approval before changing its layout or labels. `SimpleWorkspace.test.tsx` checks it.

In the simple view, an applied edit and a call a dialogue pass wasn't sure about open in the same card, right on top of the timeline (`.edit-card`), with nothing drawn between the card and the passage's band. The card is one row for both: Scarlet's note, its small controls, and the decisions on the right. A cut's card has two small icons there, with no text, each named on hover: one opens its words ("Show transcript", then "Hide transcript"), and after it one plays the cut with the cut footage ("Play Before (\)", then "Back to After (\)"). Every edit, suggestion and standalone comparison uses that same icon. It is white while Before is shown, and a click or \ switches sides. A cut plays as the video runs now unless the icon is lit. A click inside the red passage on the timeline plays from that point through the cut footage and lights the icon by itself, with a flash. It stays lit until \ or the icon is pressed again, and the next cut opens unlit. A press on the open cut's row in the chat plays it again from the top, unlit, and doesn't close the card. An applied edit's card has Undo edit as a small icon before Revise, named "Undo edit (U)" on hover. A call leads with its number ("Cut 2"), the same as on its line in the chat, and says how many still wait on hover. A flagged edit still waiting on the editor leads with its place among the ones that are ("1 of 3"), since nothing else says how many are left, unless its pass still waits on calls: then it leads with its number among them ("Cut 6") and says its place on hover. It has no picker and no script icon: ↑ and ↓ step to the others. Revise is plain text and the decision (Approve or Keep) is the row's only button. The note is a small dim caption on up to two lines, so a short note leaves the card a single line. A pass that stopped early, or finished without checking some of them, hands the editor the flagged cuts it never checked, and such a call says "Not checked yet." before its note. The passage is on the card, folded behind the transcript icon: opened, it is a second row under the card's row, scrolling inside the card when long, and it folds again on the next cut. Until its words arrive it says Loading the words… beside the mark. Opened, it reads whole sentences either side of a ✂ mark where the cut joins, red once applied, amber for a call. A mark holds up to 8 removed words, struck through; a longer cut's mark gives its length and opens its words when clicked. The passage has no speaker or track tags. A note longer than two lines opens in full on a click and folds on the next; there is no button, only the pointer changes over it. Shortcuts (↑ ↓ \ R K S A U) show on hover, not in key boxes. ↑ and ↓ step to the previous and next edit or call. From a flagged edit still waiting on the editor, or one of them sent back for revision, they step to the previous and next one that waits, unless the chat lists every edit of its request, however that list came to be open: then they step through them all. ← and → are always the player's, card open or not: they skip 5 seconds, or 1 second with Shift. There is no Close button; Esc closes it. An applied edit has Undo edit (U), Revise (R) and Keep (K). U sends the undo to Scarlet at once, and once however long the key is held. An applied edit sent back for revision has no card until its new version lands: its note and decisions are about the version on its way out, and its row in the chat says Revising…. It stays open meanwhile, with the message box still aimed at it, ↑ and ↓ stepping on and Esc closing it, and the card comes back on the new version. A revision of an edit that was the editor's to check is theirs to check again, whether or not Scarlet flags it: it is amber and counted in "N need you", and its row says Revised until Scarlet gives a reason of its own. An applied edit's note is Scarlet's one-sentence summary of what the edit did, and nothing else. An edit that carries a reason to look says it inside that sentence, with no amber, no second part, no line above it and no label for the flag; the timeline already says which edit is flagged and where. An edit saved before Scarlet wrote summaries reads as its title, then its reason to look, as plain text. Keep records the review and moves to the next flagged edit that hasn't been kept, or after the last of them to the first call of the same request that still waits. Kept on an edit Scarlet didn't flag, it moves to the next edit instead, and the card closes after the last. A call has Revise (R) and Approve (A), then a small × that skips (S) and says "Skip (S)" on hover. Approve makes the change Scarlet proposed and Skip leaves it out, so the words fit any kind of edit, not only cuts. A revised call shows its version before its note; hovering it shows the earlier version and the note that sent it back. Each call moves to the next one, and the last call applies the pass with Scarlet's picks for the rest, or schedules it for when Scarlet finishes checking. A flagged edit of the same request that still waits then opens in the call's place, so the card closes only once "N need you" has nothing left. A scheduled pass waits for the editor again if Scarlet then asks about a cut they haven't called. Nothing in the chat applies a pass and nothing holds one back: once no call waits on the editor and no cut is with Scarlet, it goes in by itself, a call changed after the last included. While Scarlet still checks, the line under its calls says "Goes in when Scarlet finishes", as a status with no button. Only an apply that failed offers Retry, under the reason. A suggestion that isn't a dialogue pass opens in the same card on top of the timeline, as one row: Scarlet's words for it, the Before icon, Revise (R) and Apply (A), with Esc to close it. The keys show on hover, not in key boxes, Revise is plain text and Apply is its only button, and \ switches Before and After. The suggestion plays as its line in the chat is pressed, and only then: a strip that comes back by itself, after an apply that was refused, is paused. The editor chose this design. Get their approval before changing its layout, labels, or shortcuts. `SimpleWorkspace.test.tsx` checks it.

Learnings are rules Scarlet picked up from what the editor asked for, for one of their skills. Scarlet only offers them: nothing in a skill changes unless the editor approves, and nothing about a learning is in the chat or the message box. Learnings in the menu opens the list in a card under the header (`.learn-panel`); Esc or a press outside closes it. Each rule is one block: the rule in a sentence, as it would read in the skill; "You said:" and the editor's words it came from; when the skill already says something the rule would change, "Replaces" in amber and the skill's own words, quoted, shown only while the dropdown is on the skill they were quoted from; then "Save to" with the skill in a dropdown, Revise in plain text, Approve, and a small × that declines, as on a call's card. Revise turns the rule into a line the editor rewords in place, and stays lit while it is: Enter or a press elsewhere keeps the new wording, which shows at once, and Esc puts the rule back. The words it came from stay as they were. Approve saves the rule as the editor last wrote it, and a reason it wasn't saved goes once it is reworded. The dropdown starts on the skill Scarlet picked and lists skills by name. Approve has Scarlet revise that skill around the rule, rewriting what it contradicts rather than adding it at the end, as a new version the editor can restore from in Settings; the row says Saving… until it has, then leaves the list. A rule Scarlet couldn't save, found the skill already says, or found would change something in the skill the editor wasn't shown comes back with "Not saved." and the reason, quoting that passage. With nothing waiting the list says "Nothing to learn yet." The editor chose this design. Get their approval before changing its layout or labels. `SimpleWorkspace.test.tsx` checks it.

Use “edit” in the interface for a requested change and its conversation. Use “cut” only for an edit that removes footage. Footage Scarlet left out as it built the video from the pieces to keep is a cut too, with the footage to show for it: the engine reads it when the change is applied (`leftOutJoins`), and one Scarlet named no edit for reads “Cut”. The whole video is “the video”, never the edit, the working edit or the cut. Keep follow-up revisions in the same edit.

Use “model” in the interface for what the editor picks to run their requests, and “Scarlet” for who does the work: not “agent”, “assistant” or “AI”. The model is the same for every project and is picked in the menu’s Model row, so Project settings holds only the project’s own settings. Claude Code and Codex go by those names wherever they are listed, and signing in to either is “Sign in with …”.

Apply requested edits to the working timeline. Keep review and follow-up replies in their edit thread. “File this thread” files the entire thread. Each timeline marker and inline chat link previews an individual edit on the full project timeline.

## AI editing agents

Read `docs/AI-AGENTS.md` before changing the prompt, skills, MCP tools, perception, agent hosts or editor preferences. Use [the skill and tool ownership guide](docs/skills-and-tools.md) to decide where new behavior belongs and how to test it.

- The model makes editorial decisions, the harness (Claude Code, Codex) runs the agent loop, and Scarlet measures the footage, applies edits safely and gives the editor control. Keep them separate so a better model or harness improves Scarlet without changes here.
- Speed is measured from the editor's request to a moment they can judge. Keep tools fast and cached, and render only what changed.
- Only creative decisions reach the editor. Anything they'd have to do by hand is a missing tool or measurement.
- Give the model everything the task needs: the editor's words as said, where they were looking, notes, the thread and preferences. When it errs, look for missing context before adding an instruction.
- Write for the next model: no fixed pipelines, instructions only for observed failures, and prune rules after each model upgrade.
- The engine builds the one prompt every host uses (`GET /api/tasks/:id/prompt`). Don't build prompts in a host.
- Tools return evidence. When Scarlet overrides the model for safety or because of an editor setting, it reports each override with its evidence. No hidden modes.
- Shape tools to what the harness delivers (`packages/shared/src/capabilities.ts`); never ask the model to judge its own abilities.
- Put tool mechanics in tool descriptions, taste in skills and Scarlet's contract in `SCARLET_INTRO`, each stated once.
- Measure changes that could affect a cut with `evals/`. Never commit user media, transcripts or results.
