# How Scarlet works with AI agents

Read this before changing anything an editing agent sees or uses: the prompt, skills, MCP tools, perception (transcripts, waveforms, frames), agent hosts or editor preferences. It records the boundaries Scarlet keeps and the reasons behind them. See the [product principles](PLAN.md#principles) and [skill and tool ownership guide](skills-and-tools.md).

## What the rules are for

Every rule below serves one of these goals:

- **Speed.** Scarlet is measured by the time from an editor's request to a moment they can judge. The agent's run is part of that time, so its tools must be fast and its context complete enough that it doesn't spend turns searching.
- **The editor decides only what needs taste, or what the model isn't confident about.** Mechanical work (finding words, placing edges, sync, padding, rendering) is done by the agent and Scarlet. What reaches the editor is a creative choice, or a cut or edit the model judges a likely mistake. The model decides which; Scarlet's code doesn't flag by a fixed rule. A skill can, since the editor owns their skills.
- **Models keep getting better.** A better model or harness should make Scarlet better with no change to Scarlet. Nothing here should cap what a stronger model can do.
- **The model can only edit what it can see.** Give it the editor's full intent and measurements of the footage, then let it choose.

## Three layers

| Layer | Owns | Examples |
|---|---|---|
| **Model** | Editorial judgment | Which words go, which take survives, how long a pause should be, what a reason says to the editor |
| **Harness** (Claude Code, Codex CLI, Antigravity CLI for Gemini) | The agent loop | Tool calling, context and compaction, sessions and resume, permissions, sandboxing |
| **Scarlet** | Context, safe editing, the editor's interface | Measuring the footage, resolving exact cut points, versioning every edit, enforcing safety rules and the editor's preferences, review and playback |

Scarlet is an interface for editors and a way for AI to read the timeline and media. It is not an agent framework and not an editor with taste of its own. When code in Scarlet starts deciding what belongs in the video, or starts running the agent's loop, it is in the wrong layer.

The layers improve independently. Models and harnesses change every few months, so keep Scarlet's side to stable contracts: a prompt, tools, evidence and enforcement. Don't tie behavior to one model's quirks.

## Rules

### What the agent is told
1. **One source of truth.** The engine builds every task's system prompt and instruction (`GET /api/tasks/:id/prompt`, `taskPrompt` in `apps/server/src/services/tasks.ts`, using `buildSystemPrompt` from `packages/mcp/src/prompt.ts`). Hosts fetch it and never build prompts. A second copy, such as the Rust port that used to live in the desktop host, drifts.
2. **Give the model everything the task needs.** The prompt carries the editor's request as they said it, where they were looking (version, playhead, selection, the edit or cut being revised), their notes, the thread's earlier requests, replies and answers, and their preferences. Don't summarize or rewrite the editor's words before the model sees them.
   - When the interface knows something about the request, such as a selected edit or "review every cut", put it in the task context. The model shouldn't have to guess what the editor was looking at.
   - A request about one edit includes its name, number, summary, reason and any review check. For a staged cut it includes the cut's summary, reason and assessment. The engine looks them up from the change (`selectedEdit` in `prompt.ts`, `cutRevisionReference` in `changes.ts`). The interface sends only which edit or cut.
   - Put what every task needs in the prompt. Make the rest discoverable through tools, so the model can look closer without the prompt growing with the project.
   - When a model's mistake traces back to something it couldn't see, add that context or measurement. Don't add an instruction to compensate.
3. **Say each thing once, in the right place.**
   - Tool mechanics go in tool descriptions and schemas: units, paging, field meanings, what a result contains.
   - Editorial taste goes in skills: who is being addressed, how to group retakes, when a pause earns its time.
   - Scarlet's contract goes in `SCARLET_INTRO`: versions and changes, the time model, safety, and how to talk to the editor.
   - The editable dialogue skill describes which cuts to make or bring back for review, their pacing and the audio blend at their joins. Editor choices about a specific cut travel with the request or its review.
   - What the editor asked for this time, and where, goes in the task context (the `## Context` lines `buildSystemPrompt` writes). A context line says which cut, edit or passage; it doesn't explain the tool that acts on it.

   If you find the same rule in two of these, delete one. The [short test](skills-and-tools.md#the-short-test) decides where a sentence goes.
4. **Write for the next model.** Add instructions only for observed failures, and prefer a better tool or measurement to another sentence. Don't script the order of steps or build a fixed pipeline the model must follow; describe what's available and let it choose. An instruction the engine writes itself (a repeat check, a redo, a resumed run) says the goal and what counts as done, not which tools to call in which order. After each model upgrade, run the evals, check which rules the model no longer needs, and remove them.
   - One pacing rule is enforced, for speed: on a dialogue first cut, `dialogue_scan` stops handing out new pages after two until the model saves the cuts it has decided or says none are ready (`noCutsReadyThrough`), and one save holds at most `FIRST_CUT_BATCH_SIZE` decisions (`packages/mcp/src/dialogue-scan-batch.ts`). Left alone, a pass read a whole recording before its first save, and the editor waited for all of it before judging anything. The rule sets when to save, not what to cut, and each refusal says what to do next. A pass is also finished only once `dialogue_check_repeats` has nothing outstanding on the current version; a pass that stops before that is sent back with that goal (`queueRepeatCheck` in `apps/server/src/services/tasks.ts`). That check lists the picture too (`pictures`, `packages/mcp/src/picture-check.ts`): each picture on screen for under a second between two others, and each stretch where a recording laid over the main picture is off it while it still shows what it showed, with the words said there and any of its text read aloud. Each counts until the pass changes the picture there or keeps it with its reason. Reported only in each save's result, a pass on project 88 left 0.45 s of camera between two screen clips and the camera up for 13 s while the speaker read his prompt off the screen, both named on that save (2026-11-21); it was the fifth report of the screen coming and going while the speaker talked about it.

### Tools and perception
5. **Scarlet measures; the model decides.** Tools return evidence: words, levels in dBFS, voice activity, frames, retake groups, room tone, loudness. The model makes the editorial call.
6. **Enforce safety and the editor's review decisions, and report each adjustment.** Scarlet may move an edge onto measured silence, hold a cut whose edge it could not place safely for the model's closer look, or keep a revised cut open for the editor who sent it back (`heldRevised` from `dialogue_review_save`). The model gets the reason and evidence for each adjustment. A held cut is the model's to settle (cut, keep, move the edge or ask); it reaches the editor only when the model asks, or unchecked when the pass stopped early. A held cut whose edge stays in sound says what the join plays and, for a range given in seconds, the nearest quiet or low point either side and which words moving there keeps or removes (`inSoundEvidence` in `dialogue-join.ts`, `joinPlays` in `dialogue-plan.ts`). For words the model named it says only that they run together where they part: offered the other words a low point would keep or take, a pass resent cuts with them and broke the sentence. Nor does a cut that would take a held cut's place with other edges apply by `unsureJoins` cut: the held cut stays where the model placed it, and the save names the cut left out (`heldCutsStay`). Held at “thing. ‖ And so in this video”, a closing save cut “And so” as well, at another join Scarlet couldn't place, and it applied with no call (2026-11-18). A named edge between two words said straight through, which the transcript times as touching, isn't held at all: it goes where the transcript parts them and applies, and the gate says so. The published editor's cuts in running speech on Muse sat 13–35 ms from that boundary, all five, and the editor's own pick on another recording 12 ms, where the lowest level and the sharpest change in the sound were up to 96 ms off; held, a pass cut other words to get round one such join (2026-11-18). A short word with such an edge on both sides stays held. An edge inside a word that is sounding there is never applied as placed (`unsureJoins` cut skips it) and `dialogue_review_save` refuses to ask the editor about it or cut it there: a clipped word is not a creative call. Of 18 calls one pass handed the editor, 15 were held in sound and asked about as "listen for the end of …", and most were a word or a few frames off (2026-11-16). Handing such cuts back to the model at save instead was tried and dropped: a pass then sent every save with `unsureJoins` cut, and passes that resent them by other words broke more sentences. A call's note quoting words its cut neither removes nor plays beside is refused (`quotesAwayFromCut`): one note described a restart four seconds on. A pass whose staged cuts the model settled, every one, without asking goes into the video when its run finishes (`applyChoicesWhenDone` in `apps/server/src/services/changes.ts`). The window used to do that once it saw the finished run, so with no window watching the settled cuts stayed out: one pass left waits of 10 s and 8 s in the edit that way (2026-11-15). `dialogue_review_save` says so when nothing is left to decide, since passes otherwise removed those cuts a second time with `timeline_propose`, three refused calls a pass. What Scarlet measured travels as `held` on the cut, apart from `reason`, which stays the sentence the model wrote for the editor. A dialogue plan can request an audio-only crossfade in project frames. Scarlet saves the overlap on the change, uses it for preview and approval and reports any join whose source handles cannot accommodate it (`joinCrossfades`). A cut staged because nothing Scarlet measures can settle its join (`unheard` on the cut, a same-word join) is the editor's from the moment it is staged: a later cut sent over its footage is set aside (`heldForReview`) until the model records a keep on it, and the pass can't move it with `dialogue_revise_cut` (`cut_unheard`): one moved such a cut onto the take that replaced the false start, where both edges were quiet, recorded it as a cut, and the broken take played with no call. A pass staged the right cut of a restart, applied a cut of the take that replaced it over the same footage half a minute later, and its review ended with no cut on the line (2026-11-17). Any other staged cut that a save's cut takes part of leaves the review as before, and the save now says so with how much of its footage plays on (`droppedFromReview`). Never silently change, invent or drop the model's work. `timeline_propose` refuses a ripple whose edge falls inside a word that is sounding there and points to `dialogue_apply_cuts`: on one pass three removals of dialogue skipped every edge check that way. The same holds for every audible clip edge an edit makes, whichever op makes it (`newClipEdges` in `packages/mcp/src/server.ts`), and for a sound the transcript has no word for: an edge that would leave a piece of a sound playing, with the sound running on into what was removed, is read from the levels alone (`clipEdgeSound` in `dialogue-join.ts`) and refused with the quiet second beside it. A pass that built its video from added clips began one 40 ms before an “uh” ended, and the revision the editor asked for trimmed that join one frame into the next word and reported the word whole (2026-11-12). `timeline_first_cut` moves such an edge onto that quiet itself and reports it (`movedEdges`), and refuses a keep range that ends inside a sounding word. On that pass's 350 edges the check names 11. An applied speech cut whose edge sits within `SPEECH_BESIDE_EDGE` (0.06 s) of the sound it removes keeps its edge, and the gate reports how close the sound is: a join can measure silent and still show a word starting in the picture (a cut 38 ms before “and”, 2026-11-13). Whether it needs the editor is the model's call (item 14): it can give any applied cut a `check`, which flags its edit until they keep it. Never silently change, invent or drop the model's work: `dialogue_apply_cuts` also says when confident cuts wait for the editor instead of applying (`stagedForEditor`, with why), how far putting cuts on whole frames moved them (`onFrames`), and which of an earlier part's staged cuts left the review because a later edit broke up their footage (`droppedFromReview`); `timeline_propose` lists each removal it put on whole frames (`onWholeFrames`), inside a selected passage too.
7. **No hidden modes.** A tool can depend on its arguments, the footage, harness capabilities, editor settings and the task’s recorded operation and scope. Pinning or reading a guide selects advice. A built-in dialogue shortcut additionally records the editing operation the editor requested.
8. **Capabilities, not self-assessment.** `packages/shared/src/capabilities.ts` records what each harness actually delivers to its model (images, audio, file writes, and the prefix a harness gives Scarlet’s tool names). Tools and prompt text adapt to it. Never ask the model "only if you can hear WAV". Claim a capability only after confirming the harness forwards that content type from MCP results in headless mode.
9. **Every model gets a way to check its own work in text and numbers.** `timeline_transcript` reads the edit in playback order, and `timeline_join_audit` measures each join as heard. Its `pictureEntrance` reports the signed time from the incoming picture frame to the first word when the visible and audible takes match. The brief or a custom skill sets the desired pace. `dialogue_check_repeats` also reads each played join letter by letter from the speech model's frames (`hearJoin` in `apps/server/src/services/dialogueRepeatAudit.ts`): a kept word heard short at the edge, or letters the transcript has no word for, is a join the editor would send back. It also lists phrases the transcript's words play twice within a moment (`findRestarts` in `packages/shared/src/restarts.ts`), including a first attempt said again with one word added or dropped ("how mechanical watch, how a mechanical watch"), a contraction compared as the word it starts with ("and then I will … and then I'll"), and a restart inside the first attempt of a longer match: one pass's edit kept "Sam Altman hasn't read a… Sam Altman hasn't read a line of code" because the list paired the hook's "read a line of code" with the headline's and skipped what lay between (2026-11-16). It reads what the edit plays in the verbatim words the pass's own scan pages saved, and in the transcript only where no page was read (`savedWords` in `dialogueDetections.ts`): the transcript tidies restarts away, and on eight passes of one recording 5 to 8 restarts per edit were in the scan's words and not the transcript's ("up to 1,286, up to 1,286", "This is a, this is"). A word doubled on its own is left to the letter-by-letter reading: on that edit the transcript's "So So" was one "So" with the second word timed over a pause. `timeline_transcript` marks the same words with a `+ heard` line where the scan's saved reading plays a run the transcript left out (`heardOnlyVerbatim` in `packages/mcp/src/timeline-perception.ts`): on three passes after the closing check listed restarts from the scan's words, the model kept many with reasons quoting the tidied transcript ("the incomplete readings were already cut before it"), since its own read-back showed the phrase once (2026-11-17). Audio and images are extras for models that can use them. Receipts that gate a decision must record a measurement that happened, not that a file was attached.
10. **Refer to content, not guessed times.** The model can name words by transcript index (`fromWord`/`toWord`) and let Scarlet resolve the exact edge from measured silence (`packages/mcp/src/dialogue-join.ts`). A pause is named by the word it follows (`afterWord`), and the model can set its remaining duration (`leave`): pause ranges typed in seconds left a median 0.54 s where the published cut of the same footage left 0.25 s. That pause plays before the cut. A range given in seconds takes `leave` too, and its edges that sit in quiet then go where that pause puts them, as a word reference's do: half of one pass's cuts were ranges typed from word times, and two of their joins played 0.45 s and 0.4 s of quiet after the last word where its skill asked for 0.14 s (2026-11-17). How soon the voice follows the cut is its own number (`voiceIn`), which a skill can state: as a share of the pause it grew with the pause, and on a 105-cut pass the voice came in a median 0.12 s after the picture cut and 0.21 s after a tenth of them, where the published cut of the same footage plays 0.07 s (2026-11-16). Where two words run together with no pause, a word reference's edge goes at the lowest level between them when that is down at room tone (`DIP_DBFS`) and the removal's other edge has a pause, and the gate says what was measured: without it every cut of a doubled word was held for the editor (20 of 25 held cuts on one pass). An edge given in seconds that lands on speech goes the same way to a room-tone dip at the nearest word boundary, within a fragment's reach. A shallower low point (`LOW_POINT_DBFS`, -44 dBFS and 10 dB under the sound either side) takes an edge within 50 ms of it, given in seconds or where a word reference's words part: edges two and three frames inside "you" and "that" sat beside such low points and the editor asked for the cut on them. Scarlet's own search further off keeps the -48 dBFS bar, since the stop before a final "s" reads the same. A dip edge sits in the middle of the room tone there, not on its lowest bucket, which is as often the last before the next word. The engine rounds a removal inward to whole frames, and a placed instant between two frames left up to a frame of the removed word playing at the join, so an edge Scarlet places is saved on the version's frame nearest to it inside the same quiet run or dip (`edgeOnFrame`), and an edge given in quiet whose inward frame has sound goes on a quiet one. Measured as saved, one pass's applied edges went from 11 of 105 on speech to 5. A word range held for want of quiet comes back with any other range that leaves the same words playing and has quiet at both edges. Where a restart lets the same words play from either saying, `dialogue_check_join` can show comparable word ranges and the evidence for their joins. The model selects the occurrence, and the planner preserves that selection. Every removal's edges are measured, a production aside given in seconds included: one without its quote skipped the check, and passes applied cuts that ended in continuous speech when they resubmitted held asides in seconds (2026-11-15). Quiet is measured against the recording's own floor as well as fixed levels (`quietRms` in `packages/mcp/src/gap-sound.ts`): on a recording with room tone near -70 dBFS, the dip between two words said in one breath measured -40 dBFS and passed for quiet. The floor is the quietest fiftieth of the page's levels, and the deep troughs an edge may sit in (`valleys`) are held to it too: under a fixed -54 dBFS a breath 10 dB over the room was a trough. A removed word with no time of its own (one the aligner found no sound for) doesn't mark where a removal's sound starts: measured from it, an edge went to a dip in the kept word's tail with half a second of silence after it. Replaying one pass's plans through these, applied edges on speech went from 8 of 162 to 1 of 149. Mapping between source and timeline time is a tool's job (`timeline_at`), never arithmetic in a prompt.
11. **Fix perception at the source.** Better measurement beats compensating instructions:
    - Local transcription uses Whisper large-v3-turbo, 5-bit (`bundledWhisperModel` in `apps/server/src/transcribe/localModel.ts`): base misspelled names and smoothed stutters and restarts into the sentence meant, hiding what a dialogue pass cuts.
    - Word times come from Whisper refined by wav2vec2 CTC forced alignment (`apps/server/src/transcribe/wordAlign.ts`, `ctcAlign.ts`). This cut the median word-start error from about 90 ms to about 40 ms on a real recording. A word the alignment doesn't confirm keeps Whisper's estimate, which can run seconds over a pause: "now." was placed on the 1.3 s of quiet after it, the transcript showed no pause, and a pass cut from the next word and left the pause in (2026-11-15). So each run of words is searched with the next run's first words as context, since its search reaches past its last word into speech that word would otherwise take; a word whose letters the search found more than half a second apart is not confirmed; and an unconfirmed word is kept on the sound its estimate covers, in Scarlet's quiet (`QUIET_RMS`, `QUIET_PEAK` and voice activity), taking no time where there is none. On three recordings (50 minutes), quiet inside word spans went from 312 s to 0.2 s and pauses the words hid from 71 to 0 (`apps/server/scripts/bench-word-timing.mjs`). Pauses, `leave` and every gap a tool reports are measured from these times, so a skill's pacing is only as good as they are. A transcript keeps the times it was aligned with, so the join check also reads a word where the recording has it when its timing can't be right: timed too short to say, on sound a neighbour's timing holds, beside speech no word explains (`onTheirSound` in `packages/mcp/src/dialogue-join.ts`). A transcript aligned before numbers were spelled timed “5.5” in 80 ms at the start of the “and” after it, with the second of “five point five” before carrying no word; a cut of the restart “and the… and GPT” was held for want of quiet between “5.5” and “and”, and the closing check kept the restart, since an edge in the quiet seemed to take “5.5” with it (2026-11-17). The moved word keeps its transcript times as `timed`, and the cut's evidence says it moved. On two recordings (85 minutes, 8,500 words) it moved that one word.
    - Waveforms decode at 16 kHz so sibilants and breaths register (`packages/render/src/waveform.ts`). Bump `WAVEFORM_CACHE_VERSION` when the decode changes.
    - The aligner's output for a recording is inferred once and kept beside its waveform (`apps/server/src/transcribe/emissions.ts`). The transcript's alignment and every scan page's read the same frames, so a page whose audio the transcript has covered aligns in milliseconds. Bump `alignmentVersion` when the model or the search changes.
    - A gap in the transcript is not a pause until the recording says so. `transcript_get` follows each gap of 0.4 s or more with what sounds in it (`packages/mcp/src/gap-sound.ts`): quiet, or sound at speaking level that no word explains. A pass that read only words trimmed "You can <1.7 s> see" as a pause; it held a first "see" and a second "you can" the transcript had missed. `dialogue_apply_cuts` leaves out a pause trim whose range holds such sound, with where it sounds and what Whisper reads there on its own (`notSaved`), so the model decides on words, not on a sound it can't hear: one such stretch was a second “but it hasn't all been great” the transcript had folded into “I'm”. A trim removes quiet; applied with a note, as it once was, one took the “5.5” out of “Opus 5.5”, which the transcript had timed at 80 ms beside a second of “five point five” (2026-11-16). The aligner spells a number the ways it is likely said and keeps the reading that explains the sound best (`spokenNumber` in `ctcAlign.ts`); one it still can't place keeps to a stretch of sound long enough to say it (`keepOnSound`). Read as a wildcard, “$7.63” ended before its “three”, the next word took that sound, and a pass cut the three with it (2026-11-17). `dialogue_apply_cuts` also lists the sound a saved part still plays between two kept words (`unexplainedSound`). No harness delivers audio to the model today (`capabilities.ts`), so what an editor would hear has to reach it as a measurement or a picture: `sound_picture` draws a passage's waveform over its spectrogram with the words at their times, and the passage again with a removal out (`packages/render/src/soundPicture.ts`). A model that can hear gets the passage's audio with it.
    - Whisper can skip a remark after a long wait and resume at the next sentence. Once a local transcript's words are placed, each stretch of a second or more without words that holds sound at speaking level is read again on its own, all of them laid end to end in one run, and the words heard are placed and saved with the rest (`apps/server/src/transcribe/transcriptHoles.ts`). On a 45-minute recording that read 10 s of audio in under a second and found five such stretches, one a second “which includes computer control” the transcript had smoothed into the first.
    - A pause trim joins the words either side of it, so where they are the same word the pause was the gap of a restart: `dialogue_apply_cuts` returns such a trim like a speech cut that plays a word twice ("every single ‖ single pastry" and "equals B7 ‖ equals B7" were saved as pauses on one pass). A cut that stops within `SLIVER_SECONDS` (0.1 s) of a join an earlier save made goes on to it, since the frames between play as a flash: one pass left four of 1-3 frames. `timeline_transcript` quotes at each join the words it took out of the recording (`took`), so a read of the edit shows a cut that took a word the sentence needs.
    - A pause is measured by level and voice activity, so typing, a breath or a cough splits one long wait into slivers. `dialogue_scan` also lists every stretch without words (`silences`), with the voice-like sound in it and how much of each picture changes through it and when. `dialogue_apply_cuts` reports the ones a saved part still plays and didn't decide (`keptSilences`), the shorter pauses it still plays with its cuts out (`keptPauses`) and the words it plays twice in a row (`repeatedWords`, `packages/mcp/src/dialogue-leftovers.ts`): a pass reads the recording, not the edit it leaves, so until then nothing showed it a wait it trimmed too little, a restart it missed or a word one of its own joins doubled.
    - A screen recording says much of what it means in its picture: a menu, a setting, a line of code, a slide. `screen_text` reads the words on screen with PaddleOCR's text finder and English reader through ONNX Runtime in the audio helper (`apps/server/src/transcribe/screenTextModel.ts`, models pinned with checksums), a frame a second, reading a frame again only when the picture changes and a line again only when its pixels do. Each line comes back as a span of source seconds with its box in the frame (`apps/server/src/services/screenText.ts`). A video is read a minute at a time and kept beside its waveform; once the model asks about a video, the rest of it is read in the background, which a pause of the project's media work holds. On a 4K screen recording read at 1920 wide (M-series CPU, 2026-11-13), a chart that never stopped moving read at about 19 s per minute of video; decoding on the CPU there was five times as fast as VideoToolbox, so only CUDA decodes it on the GPU. Bump `SCREEN_TEXT_VERSION` when the reading changes.
    - A punch-in or a vertical crop that cuts off a head is a framing made without knowing where the head is, and a contact sheet shows only a few moments. `faces` finds the faces in a video's frame with YuNet (OpenCV Zoo, MIT, 230 KB, pinned with a checksum in `apps/server/src/transcribe/faceModel.ts`) through ONNX Runtime in the audio helper. A video is decoded four frames a second at 640 on its longer side, a minute in one pass, since separate seeks decoded up to a keyframe interval (8 s on a 4K camera file) again each time; faces are looked for twice a second, and in the frame between two looks whose faces differ. Each face is followed as a track by position, not identity, and its time split into spans over which its box stays within 1.5 times the face each way and it doesn't turn 45° from where the span looks: a span gives the box that holds the face throughout, a rough yaw from where the nose sits between the eyes, and the detector's confidence (`apps/server/src/services/faces.ts`). It is kept beside the waveform and read in the background as screen text is (`pictureReading.ts` holds what the two share), and tracks are worked out from the kept frames on each call. On a 58-minute 4K talking head (M-series CPU, 2026-11-15) the first five minutes read in 17 s, 3.5 s per minute of video; the whole recording took 5.5 minutes, 5.7 s per minute, while other work held the Mac at a load of 15-27. The presenter came back as one track of 261 spans, a toy on the shelf behind as a second at confidence 0.62, and asking again took 25 ms. Bump `FACES_VERSION` when the reading changes.
    - A camera laid over a screen recording as an inset was the whole wide shot shrunk into the corner: the presenter a small figure off centre, beside a mic arm and a shelf. Every model left it uncropped (Gemini 4 Neon and GPT-6.2 Sol, 2026-11-19 and 20), though `insetLook` showed them the inset after the save, and the editor asked why the camera wasn't framed. An editor's skill that asks for an inset 20% larger, 1.5:1, from above the hair to the desk with rounded corners is a crop worked out from where the face is, arithmetic a model gets wrong as it does a zoom. So `timeline_first_cut`'s layer and `timeline_propose`'s `pictureLayout` place the inset on the presenter (`presetInset` in `packages/mcp/src/sync-layout.ts`), and `presenter` takes the skill's terms: `show` (head, shoulders, chest or desk), `aspect`, `size` against the preset and `cornerRadius`. `faces` is read over six ten-second stretches spread across the source the inset plays, and one crop of that shape is placed from where the eyes and face keep to for all but a tenth of that time, in face widths above and below the eyes, since a crop can't be keyframed. Head and shoulders in the video's shape at the preset size is what it places when the model asks nothing. A second face that shares the picture for a quarter of the presenter's time, none, or faces not read in time (the save waits up to 20 s for them; an unread 4K camera reads its six stretches in about that) leave who to show to the model: the inset keeps the camera's whole height, cut to the shape asked from the middle. The result says which, with the crop. `framing` still sets the transform outright. On the 4K camera of 2026-11-20 the skill's terms cut the sides to 1.5:1 from just above the hair to the bottom of the picture, the presenter centred and the mic arm out.
    - A zoom on part of a screen recording is a frame of the video's shape placed on the source, and working one out from a transform is arithmetic the model gets wrong in a predictable way. ### The editor's attention
14. **Only creative decisions and likely mistakes reach the editor, and the model decides which.** If the editor would have to do something by hand, such as nudge an edge, re-sync a track or find a passage, that's a missing tool or measurement, not a review item. A skill is different: it is the editor's to customize, so a specific rule in one ("a kept silence of 2 s or more goes to review", "tighten pauses to about a quarter second") is their decision, and the model applies it. The folders the machine's TLS settings point at (`SSL_CERT_FILE` and the like) are readable too: on one machine `curl` used a Python package's bundle and failed every https address in Codex's sandbox. Claude Code gets `Bash`, `Read`, `Write`, `Edit`, `Glob`, `Grep`, `WebSearch` and `WebFetch`, with its sandbox on, `autoAllowBashIfSandboxed`, `blockReadsOutsideWorkingDirectories`, every domain allowed to the sandbox's proxy and `WebFetch(domain:*)`. Codex keeps its shell and `view_image`, searches the live web, and its permission profile opens the network and reads only the programs' folders outside the workspace. agy keeps `--sandbox` for its terminal, and Scarlet's permission handler allows its own tools unless a call names a path outside the task folder and the programs' folders (`workspacePermission`). That is as far as Scarlet reaches there: agy 1.5's file tools read inside the workspace without asking, its terminal reads outside it, and its terminal has no network and agy no page-fetch tool, so a Gemini run reads the web through `web_capture` and search.
    - Scarlet's token never reaches the model. No CLI is given Scarlet's own variables (`workspaceEnv`, `workspace_env`): Codex passes them to Scarlet's server from its own and keeps them out of the shell (`shell_environment_policy`). Claude Code's control files (`.scarlet`, whose `mcp.json` holds the token) are closed to every tool and to the shell. With a shell and the web, a model holding the token could call the engine directly and go round every check on an edit.
    - It costs every request the tools' definitions on every turn: on Claude Code the first turn went from about 52K tokens to about 60K (one measurement, 2026-11-21); Codex sends far less of its tools a turn. Two dialogue passes with them on never ran a shell command or a web search, and scored 81.8% beside main's 83.7% on the standard scorecard, within what luck gives; restarts left in fell from 97.6% to 70.2%, inside that day's range for near-identical code (66–98%), so two passes didn't settle it.
    - Claude resumes its own session after the editor answers a question (`--resume`), and after a run is cut short: by Scarlet quitting, by a lost worker, by the host's stall or time limit, or by Pause. Pause hands the session to the attempt that Resume starts when it runs on the same model, and marks the paused attempt `sessionCarriesOn` so the host keeps its session; Stop this edit ends it. Every attempt at one run shares the first attempt's task folder so the session is found again. If the host no longer has it, the run starts fresh with the engine's recap.
    - Codex runs use App Server threads over stdio and forward cumulative usage during the turn. The hosts give App Server a private Codex home beside the task folder, linked to the existing file-backed login, and keep the thread there, so an answer, an interruption or a pause resumes it (`thread/resume`) as Claude's session is; a resumed thread's usage is counted from where it picks up. When App Server cannot start with that isolation, the hosts use ephemeral `codex exec` (with `project_root_markers=[]`, so no enclosing repository's AGENTS.md loads), which reports usage only at turn completion: a run it stops for a question or a cancel records no tokens. An exec run that is answered or interrupted starts afresh with the earlier questions and answers, or the recap, in the prompt.
    - Gemini runs through Antigravity's `agy acp`. The prompt goes in `_meta.antigravity.systemPrompt.append` on the session, since agy cuts GEMINI.md at 24 KB; a run whose agy doesn't offer it in `initialize` stops and says to update agy. Scarlet's permission handler allows a tool only when agy names the scarlet server, or names one of Scarlet's tools exactly (agy shows them as `mcp_scarlet_<tool>`), never by its display title, which agy takes from the model's own words. A refused tool ends agy's turn, so the run carries on in the engine's words (`refusedTool` on the prompt), at most four times. Gemini runs aren't resumed, and agy still runs in the user's own agy home: their own agy MCP servers share its tool budget.
    - Don't rebuild compaction, memory or planning inside Scarlet.
    - Requests run one at a time in a project, except requests that are each about one cut or edit and about different ones: those run at once, an agent on each (`queueBlocker` in `packages/shared/src/threads.ts`, which the engine's claim calls). Nothing locks footage while they work. Side checks (an area check, a learning check) save nothing to the video and run in slots of their own on a host, twice its request slots (`sideCheckSlots` in `packages/shared/src/api.ts`), with a running request's area checks claimed first: sharing its slots, an edit held one while its 20 area checks queued for the other two (2026-11-20). A call's revision is saved into the pass as it stands when it lands. An applied edit's revision is replayed onto the current video through the footage (`planApply`), and one that meets footage changed since its base version is not applied: `timeline_propose` returns `notApplied` with what met and the current version, and the agent makes it again there.
    - The agent's plan is the harness's own to-do list (Claude Code's `TaskCreate`/`TaskUpdate`, Codex's `update_plan`), read from the CLI's stream and recorded as `plan` task events: each step in the agent's words, pending, in progress or done. It is evidence, never an instruction: Scarlet sets none of its steps. The chat doesn't show it: since 2026-11-10 a working request shows one line of what Scarlet is doing this moment, which the editor chose over stages and plans. So no harness is launched with its to-do tool (`plan` is off for every agent in `capabilities.ts`), and no run pays the median of about 15 seconds the plan cost a request on 2026-11-08. `SCARLET_AGENT_CAPS='{"plan":true}'` where the engine runs turns it on: the engine then launches a run with the tool, and with one paragraph of the prompt (`PLAN_STEPS`) asking for the steps, except a dialogue pass, a request about one staged cut and a skill edit (`taskPrompt` in `apps/server/src/services/tasks.ts`). Given the tool and no word about it, the agent made no plan in six real requests; asked, it listed three to five steps within twelve seconds in each of eleven. Codex App Server reports each step’s status. The exec fallback reports which steps are finished.
16. **Keep the user's environment clean and runs observable.**
    - Delete task control files that hold the access token once a task ends or pauses on a question (the attempt that resumes writes them again), and prune old task folders.
    - Remove a finished run's Claude session directory, and with it the to-do list Claude Code keeps for each of its sessions (`~/.claude/tasks/<session id>`), under `CLAUDE_CONFIG_DIR` when that is set; a task folder whose path is too long to name whole is found by Claude Code's `<first 200 characters>-<hash>` name and a session that records its folder. A run that was cut short keeps it for the attempt that resumes it; the task folder's prune removes it if nothing does.
    - Stop a CLI with SIGTERM to its process group and SIGKILL five seconds later, so Claude Code can write its session first. Stop agent CLIs an earlier launch left running (a crash signals nobody; the TypeScript host doesn't sweep on Windows), except those of another Scarlet that is still open, and at exit hard-stop the process group of each CLI stopped in the last few seconds (Windows has nothing left to finish: its stop ends the whole tree). The launch sweep recognises a process by its id, program and start time, because a freed id sooner or later belongs to another program.
    - Report each run's tokens, including runs that pause for a question (`POST /tasks/:id/usage`). When the harness reports usage during the run, send cumulative snapshots to the same endpoint and write the final total after the pending snapshot. The edit thread estimates API cost from reported tokens and published standard rates. Billing is handled by the provider.
    - Never put API keys in a run that should bill the user's subscription.
    - Claude Code runs with `--restricted` (no user settings, hooks, plugins or CLAUDE.md) and `--strict-mcp-config`; a side check's has `--tools ""` and only Scarlet's tools allowed. Its tool deadline (`MCP_TOOL_TIMEOUT`) is at least 300 s whatever the environment says, since Scarlet's waits are measured against it.
17. **Skills load progressively.** The workflows Scarlet comes with appear as one line in the prompt and are read through `skills_list` when needed. An editor's own house rules and explicitly selected skills are included in full.
    - A skill builds on others by calling them in its text, `/frame-screen` at the place it applies with what it changes beside the call, or by naming them in its header (`extends:`). Scarlet puts every guide it calls in the prompt ahead of it, in the order called, and those guides' own in turn (`skillExtends` in `packages/shared/src/threads.ts`, `assistantSkills` in `apps/server/src/services/skills.ts`). A guide a skill only names in passing is read when the model chooses to open it, which it doesn't always. What suits every editor belongs in the shipped guide; an editor's own skill holds what is theirs.
    - The skills in `skills/` are added to a new library once and are the editor's from then on. There is no separate Scarlet version of a skill.
    - A changed `SKILL.md` reaches installed copies the editor hasn't edited. An edited copy is theirs and is never changed or merged.
    - The editor can change a skill by saying what they want (the chat beside its instructions in Settings). That is a `skill_edit` task: its prompt is the skill as it stands, the editor's words and `SCARLET_INTRO` for reference, with no project in it, and its only tools are `task_log`, `task_question`, `skills_list` and `skill_save_edit`. The tool saves to the one skill the editor asked about. The model supplies the description and instructions; Scarlet keeps the name, the rest of the header and the earlier version. Agent runs belong to a project, so the task borrows the one worked on last, and stays out of its conversation and its queue.
    - A skill can also learn from what the editor asks. Every request is read for a standing rule as it is sent, by a `learning_check` task: a short run with the request's agent and model that starts beside the request, outside the project's queue and its conversation, so a rule reaches the editor in seconds and whether or not the request finishes. Its prompt is the editor's words, what they were aimed at, what they asked earlier in the project, their skills by name and description, and the rules Scarlet already has; it sees no footage. It offers a rule only when the editor states one themselves (about every video, not this one) or when at least two of their earlier requests asked for the same kind of fix to what a skill made; a single note about one cut, a rule the skill already has in other words, and a rule that only says to do the work well are not offered (2026-11-20). Its only tools are `skills_list` and `learning_suggest`: one sentence, the skill it belongs in, and what that skill already says that the rule contradicts or overrides, quoted word for word. It reads that skill in full before offering, so a rule the skill already has isn't offered and the editor sees what a rule would change before deciding. Scarlet checks each quote is in the skill and sends back one that isn't. The run that edits has no such tool, so the same rule never arrives twice in two wordings. A message that only names a skill, a request Scarlet made itself, and a resumed or retried run aren't read. The check waits while editing is paused, and stops when the editor takes the request back (⌘Z), but not when they stop it: a rule reaches them whether or not the request finishes. Scarlet keeps a rule with the editor's words (a learning) and changes nothing. The editor reviews learnings in the simple view's menu; approving one starts a `skill_edit` task whose instruction is the rule, what they said and what they were shown it replaces. The save applies the approved rule within the chosen skill and preserves content outside the approved replacements. If it finds the skill saying otherwise somewhere the editor wasn't shown, it saves nothing and quotes the passage, which comes back to them under the rule as why it wasn't saved; approving again tells the next save they have read it. It runs on the model chosen when they approve, not the request's, which they may have left. A skill's edits run one at a time, so a second approval for the same skill starts when the first has saved. Never save a rule the editor hasn't approved.

### Evidence
18. **Measure every change that could affect the cut.** Use `evals/` (see `evals/README.md`):
    - Score finished tasks: edges on speech, clipped words, removed time by kind, agreement with the editor's decisions.
    - Replay stored plans through new code.
    - Run several trials per model and harness. Rerun them when a new model ships, both to compare it and to find instructions it no longer needs.

    Grade outcomes with code; use LLM judges only for trend dashboards.

## Checklists

**Adding or changing an MCP tool**
- Does it measure or apply? Policy belongs in a skill or an editor setting instead.
- Is it fast enough to call in a loop? Cache what it computes, and answer a range in one call.
- Add its annotation, compact output, units and an actionable error.
- Gate it on capabilities if it returns audio or images or needs file access.
- Update the tool inventory, UI labels, skills that mention it and tests.
- Confirm no other tool, skill or prompt line already explains the same thing.

**Changing the prompt or a skill**
- Is there an observed failure behind it? Could missing context or a better measurement fix it instead (rules 2 and 11)?
- Put the text in the right layer (rule 3, and the [short test](skills-and-tools.md#the-short-test)) and delete the duplicate.
- In a skill, name a tool; don't explain it. Don't put scope, permissions or anything Scarlet enforces in a skill.
- For `SKILL.md`, keep frontmatter `name` and a `description` that says when to use the skill.
- Run the evals on a real case before and after.

**Adding something the editor reviews**
- Does it need taste? If a measurement could settle it, let the agent or Scarlet settle it and report the evidence.
- Can the editor judge it from the changed moment alone, with its before and after?

**Adding a perception signal**
- Compute it in the engine or the MCP package, and cache it with a version in the cache key.
- Expose it as evidence, not as a decision.
- Check licenses: Scarlet is MIT and used commercially, so non-commercial model weights are out.
- Download models from a pinned URL with a sha256 check (see `localModel.ts`).

**Supporting a new harness**
- Add a runner in both hosts (`apps/agent/src/runners`, `apps/desktop/src-tauri/src/host`) that fetches the engine's prompt.
- Give a request the harness's own shell, file and web tools, sandboxed to the task folder, with Scarlet's token out of their reach; give a side check Scarlet's tools only.
- Add its capabilities only after testing them headless.
- Make sure its sessions don't leak into the user's own history.
